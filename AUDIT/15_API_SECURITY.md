## F-API-01 — CRITICAL — Unauthenticated arbitrary file upload with the service-role key

**Finding.** `POST /api/media/upload` accepts a multipart upload from **any caller**, with no
authentication, no authorisation, no rate limit and no content validation beyond a
client-supplied MIME string — and stores it in a **public** Supabase Storage bucket using the
**service-role key**, which bypasses every storage policy.

**Evidence.**
```ts
// app/api/media/upload/route.ts
:5   const serviceKey = process.env.SUPABASE_SERVICE_ROLE_KEY || process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY || ''
:7   export async function POST(req: NextRequest) {          // no auth anywhere
:15    const supabase = createClient(supabaseUrl, serviceKey)
:35    const maxSize = 20 * 1024 * 1024
:48    if (!allowedTypes.includes(file.type)) { … }          // file.type is CLIENT-SUPPLIED
:58    await supabase.storage.createBucket('media', { public: true, … })
:66    const ext = file.name.split('.').pop() || 'bin'        // extension from the file NAME
:68    const path = folder ? `${folder}/${name}` : name      // folder is UNSANITISED user input
:73    const { data, error } = await supabase.storage.from('media').upload(path, file, {…})
:87    const { data: pub } = supabase.storage.from('media').getPublicUrl(path)
```
The same shape, and the same absence of authentication, exists in
`app/api/public/upload/contact-file/route.ts:7-104` (10 MB, into `contact_files`).

**Exploitability.** Trivial. No credential of any kind is required.

**Impact.**
1. **Unauthenticated storage exhaustion / cost attack** — 20 MB per request, unbounded requests.
2. **Hosting of arbitrary attacker content on the organisation's domain and Supabase project** —
   the returned URL is a permanent, publicly reachable, organisation-branded link. This is usable
   for phishing, malware distribution, and abuse of the Supabase project quota.
3. **Public bucket with no ownership model** — the `media` bucket is created `public: true`
   (`app/api/media/upload/route.ts:59`; also `automation-scripts/08:26-33`), so every uploaded
   object is world-readable and permanently public.
4. **No content validation** — the MIME allowlist trusts `file.type`, which the client supplies
   and which is trivially forged. There is no magic-byte check, no antivirus scan, no image
   re-encode. `text/plain` is on the allowlist, so arbitrary text is storable.
5. **Unsanitised path prefix** — `folder` is concatenated into the object key with no validation
   or normalisation, so an attacker chooses the key namespace.
6. **`createBucket` executed on every request** — a service-role DDL attempt per upload.

**Affected scope.** The `media` and `contact_files` buckets; the organisation's Supabase
project quota; the reputation of the public domain.

**Severity.** CRITICAL · **Confidence.** HIGH

**Recommended remediation.** Delete both endpoints. Replace with an authenticated,
authorised upload flow: (a) the client requests an upload intent; (b) the server validates the
declared type, size and the caller's permission, and issues a **short-lived signed upload URL**
against a **private** bucket with a server-generated key (`{org}/{uuid}.{ext}`); (c) the client
uploads directly; (d) the server records the object in an `assets` table with an owner, a MIME
type determined by **sniffing the bytes**, a checksum, and a scan status; (e) reads are served
through short-lived signed URLs after an authorisation check. Add per-identity rate and quota
limits.

## F-API-02 — CRITICAL — Unauthenticated arbitrary file deletion with the service-role key

**Finding.** `DELETE /api/media/delete?path=<any object key>` deletes any object from the
`media` bucket. There is **no authentication and no authorisation**.

**Evidence.**
```ts
// app/api/media/delete/route.ts
:5   const serviceKey = process.env.SUPABASE_SERVICE_ROLE_KEY || …
:7   export async function DELETE(req: NextRequest) {        // no auth
:15    const supabase = createClient(supabaseUrl, serviceKey)
:19    const path = searchParams.get('path')
:23    if (!path) { … }                                      // presence check only
:30    const { error } = await supabase.storage.from('media').remove([path])
```

**Exploitability.** Trivial, and **enumerable**: the object keys generated by
`app/api/media/upload:66-68` are `${folder}/${crypto.randomUUID()}.${ext}` and the bucket is
public, so an attacker can first `GET` the bucket listing (the bucket is public, and
`automation-scripts/08:102-104` grants `SELECT` on it) and then delete every object.

**Impact.** Total, unauthenticated destruction of the organisation's uploaded media —
avatars-adjacent assets, uploaded media, and anything else placed in that bucket. Because the
endpoint is unauthenticated it is also a permanent denial-of-service and a data-destruction
capability handed to anyone on the internet, discoverable by URL pattern.

**Affected scope.** Every object in the `media` bucket.

**Severity.** CRITICAL · **Confidence.** HIGH

**Recommended remediation.** Delete the endpoint. Object deletion must be an authenticated,
authorised, audited operation against an `assets` row (never a raw path), performed with a
user-scoped client so that storage policies apply, and constrained by a retention policy
(`50_DATA_RETENTION.md`).

## F-API-03 — CRITICAL — Contact/enquiry attachments are publicly listable, downloadable and deletable

**Finding.** The `contact_files` bucket is private, but three `storage.objects` policies grant
the `public` database role full access to it.

**Evidence.**
```sql
-- automation-scripts/08-storage-bucket-setup.sql
:40-47  INSERT INTO storage.buckets (id, name, public, …) VALUES ('contact_files','contact_files', false, …)
:125    CREATE POLICY "Public can upload contact files" ON storage.objects
          FOR INSERT TO public WITH CHECK (bucket_id = 'contact_files');
:131    CREATE POLICY "Public can view contact files"   ON storage.objects
          FOR SELECT TO public USING (bucket_id = 'contact_files');
:137    CREATE POLICY "Public can delete contact files" ON storage.objects
          FOR DELETE TO public USING (bucket_id = 'contact_files');
```

**Exploitability.** Trivial. `GET {SUPABASE_URL}/storage/v1/object/list/contact_files` with the
public anon key returns the complete object list (the `SELECT TO public` policy enables it), and
each object is then downloadable. Object keys are
`contact-{Date.now()}-{crypto.randomUUID()}.{ext}`
(`app/api/public/upload/contact-file:64-67`), which is a strongly enumerable pattern.

**Impact.**
* **Confidentiality:** brand-collaboration enquiries (`app/contact/page.tsx` has a
  "Brand / Collaboration" mode) may carry rate cards, signed NDAs, company-registration
  documents, bank details or identity documents. All of it becomes world-readable.
* **Integrity/availability:** anyone can delete any submitted attachment, destroying an
  organisation's business pipeline.
* The `MIME` allowlist permits `application/pdf`, which is exactly the format used for contracts.

**Affected scope.** All files ever attached to a contact or application form.

**Severity.** CRITICAL · **Confidence.** HIGH

**Recommended remediation.** Drop the `TO public` `SELECT` and `DELETE` policies. Serve
enquiry attachments only to authenticated staff via short-lived signed URLs. Store them under a
per-organisation prefix. Add upload rate limiting, a malware scan, and an explicit retention
period. Assume existing attachments have been exposed and assess notification obligations.

## F-API-04 — HIGH — Unauthenticated server-side request forgery and credential oracle

**Finding.** `POST /api/discord-portal/webhooks/validate` is completely unauthenticated and
causes the server to issue an outbound HTTP `GET` to a caller-supplied URL.

**Evidence.**
```ts
// app/api/discord-portal/webhooks/validate/route.ts
:4   export async function POST(request: NextRequest) {    // NO auth
:6     const { url } = await request.json()
:15    const result = await validateWebhookUrl(url)

// modules/discord-portal/webhookService.ts
:233  const urlPattern = /^https:\/\/discord(?:app)?\.com\/api\/webhooks\/\d+\/[\w\-._~!*'();:@&=+$,\/?#[\]]+$/
:242  const response = await fetch(url, { method: 'GET', headers: { 'User-Agent': 'Raptor-Esports-CRM/1.0' } })
:256  const webhookInfo = await response.json()
```

**Exploitability.** The regex constrains the host to `discord.com` / `discordapp.com`, so
arbitrary-internal-host SSRF is **blocked**. What remains is fully available to an anonymous
caller: an **unauthenticated, unmetered proxy** that will fetch any Discord webhook URL and
return the parsed result. This is useful to an attacker who has obtained a webhook URL and wants
to confirm it is live before abusing it.

**Impact.** Unauthenticated outbound HTTP on the organisation's infrastructure; an
unauthenticated webhook-validity oracle; no rate limit, so it can be driven in a loop.

**Affected scope.** Server egress; the integrity of the Discord integration.

**Severity.** MEDIUM (HIGH if the regex is ever relaxed) · **Confidence.** HIGH

**Recommended remediation.** Require an authenticated admin/manager. Perform the validation
**from the browser** instead of the server (the webhook URL is already client-supplied, so there
is no reason to proxy it). If server-side validation is required, resolve the host, reject
private/link-local/loopback ranges, follow no redirects, cap the response size, and set a strict
timeout.

## F-API-05 — HIGH — Stored SSRF: webhook URLs are stored unvalidated and then fetched server-side

**Finding.** The webhook-URL regex is applied **only in the `PUT`** handler, not in `POST`, and
not in `GET /api/discord/webhooks` (the Discord-bot route). A stored URL is later fetched
server-side by `sendWebhookMessage`.

**Evidence.**
* `app/api/discord-portal/webhooks/route.ts:172-177` — `POST` validates only that `hook_url`
  and `type` are **present**; the URL format is never checked.
* `app/api/discord-portal/webhooks/route.ts:276-281` — `PUT` calls `validateWebhookUrl` only
  `if (updates.hook_url)`.
* `app/api/discord/webhooks/route.ts` (bot route) — no URL validation at all.
* `modules/discord-portal/sendToDiscord.ts:200-215` — `sendWebhookMessage(webhookUrl, payload)`
  does `fetch(webhookUrl, { method: 'POST', … })` with **no host allowlist**.
* `app/api/discord-portal/send/route.ts` — an admin/manager can trigger a send, which fetches
  the stored URL.

**Exploitability.** Requires an `admin` or `manager` account (or a compromised one). Low
complexity: POST a webhook with `hook_url = "https://169.254.169.254/latest/meta-data/iam/…"`,
then call the send endpoint.

**Impact.** Server-side POST to an arbitrary URL, from a Vercel-hosted function, with a
caller-influenced JSON body. On a non-cloud-metadata-safe host this can reach internal services
or cloud metadata endpoints. Even where metadata is blocked, it is a request-forgery primitive
against anything the deployment can reach.

**Affected scope.** The server's network position.

**Severity.** HIGH · **Confidence.** MEDIUM-HIGH

**Recommended remediation.** Validate on **every** write path with a single shared validator;
enforce it in the database with a `CHECK (hook_url ~ '^https://discord(app)?\.com/api/webhooks/[0-9]+/')`
constraint so no code path can bypass it; re-validate at fetch time; block private and
link-local address ranges; do not follow redirects.

## F-API-06 — CRITICAL — An admin endpoint destroys the entire operational database with no confirmation, no audit and no error checking

**Finding.** `POST /api/admin/settings` with `{"action":"purge_non_admin_data"}` deletes every row
from seven tables and then every non-admin user, using the service-role key.

**Evidence.**
```ts
// app/api/admin/settings/route.ts
:103   if (action === 'purge_non_admin_data') {
:105     const tables = ['attendances','performances','rosters','slots','sessions','slot_expenses','winnings']
:115     try {
:116       for (const table of tables) {
:117         await supabaseAdmin.from(table).delete().neq('id', null)   // no .eq() filter, no error check
:118       }
:119       await supabaseAdmin.from('users').delete().neq('role', 'admin')
:120       return createSuccessResponse({ success: true }, 'Data purged successfully')
:121     } catch (purgeError) { … }
```

**Why this is worse than it looks.**
1. **No confirmation, no typed challenge, no dry-run, no two-person rule.**
2. **No transaction.** Seven sequential `DELETE`s; if the process is interrupted or one fails,
   the database is left partially purged.
3. **No error checking.** The Supabase JS client **returns** errors rather than throwing them,
   so `await … .delete()` resolves even on failure. The `try/catch` therefore **cannot fire**
   for a failed delete, and the endpoint returns `{ success: true }` regardless. This is a
   textbook silent failure (see `17_ERROR_HANDLING.md`).
4. **Service role** ⇒ RLS cannot protect anything, and no policy is consulted.
5. **No audit record.** `removeConsole` strips the production logs, so the purge is invisible.
6. **Irreversible in practice.** `performances` and `attendances` are the organisation's
   competitive record; there is no soft delete and no confirmed backup (see `51_BACKUPS.md`).
7. **The UI hosts it.** `app/dashboard/admin/settings/page.tsx` renders the control, and
   `components/ui/alert-dialog.tsx` — the confirmation primitive that exists in the repository —
   is never imported.

**Exploitability.** Requires an `admin` session. The token is stored in `localStorage`
(`09_AUTHENTICATION.md` F-AUTH-01), so any XSS yields an admin token and therefore this
capability.

**Impact.** Complete, silent, unaudited loss of all competitive results, attendance, roster,
session, and financial data, plus all non-admin accounts.

**Affected scope.** The entire operational dataset.

**Severity.** CRITICAL · **Confidence.** HIGH

**Recommended remediation.** **Delete the capability.** In V2 there is no "purge" operation.
Destructive operations are: (a) expressed against a scoped resource, never a table list;
(b) performed as a single `SECURITY DEFINER` function inside a transaction with an
`EXCEPTION` block that rolls back; (c) gated behind step-up authentication and a typed
confirmation token; (d) preceded by a mandatory, checksummed export; (e) written to an
append-only audit log that is stored outside the database being destroyed.

## F-API-07 — HIGH — Cross-tenant-shaped data exposure through `select('*')`

**Finding.** Four endpoints return every column of `users`, which includes date of birth,
home address, emergency-contact name and number, precise device telemetry, Discord and
Instagram handles, sensitivity settings, game statistics and achievements.

**Evidence.**
* `app/api/users/route.ts:41-44` `supabase.from('users').select('*')`, reachable by
  `admin`, `manager`, **`analyst`**, `coach` (own team) and **`player`** (own team) — lines 32, 47-62.
* `app/api/profile/route.ts:52-60` `.select('*, team:team_id(…), roster:rosters!inner(…)')`.
* Column list: `scripts/00-complete-schema-setup.sql:41-91` (62 columns).
* Nested selects also return other people's email addresses:
  `app/api/performances/route.ts:55` `users:player_id(id, name, email)`;
  `app/api/sessions/route.ts:52` `created_by_user:created_by(id, name, email)`.

**Exploitability.** Any authenticated player, using their own token.

**Impact.** A player can enumerate their entire team's date of birth, home address, emergency
contact details and device fingerprints. For a roster that may include minors, this is a
child-safety and privacy incident, not merely an over-exposure. It also directly contradicts
the product's own documentation (`README.md:196-200`, `API_DOCUMENTATION.md:382-389`).

**Affected scope.** Every organisation user's PII.

**Severity.** HIGH · **Confidence.** HIGH

**Recommended remediation.** Explicit column allowlists per endpoint and per role. Never
`select('*')` on a table containing PII. Split PII into a separately-protected table with its
own policy. Default every field to private; expose it deliberately.

## F-API-08 — HIGH — Mass assignment in the Discord webhook update endpoint enables cross-team escalation

**Finding.** `PUT /api/discord-portal/webhooks` spreads the entire request body into a database
update with no field allowlist, and does not repeat the `type`-elevation check that `POST` has.

**Evidence.**
```ts
// app/api/discord-portal/webhooks/route.ts
:241   const { id, ...updates } = await request.json()
:265   const canEdit = userData!.role === 'admin' ||
:266     (userData!.role === 'manager' && existingWebhook.team_id === userData!.team_id)
:283   const { data, error } = await userClient
:285     .from('discord_webhooks').update({ ...updates, updated_at: new Date().toISOString() })
:287     .eq('id', id)
```
The `POST` handler contains a check that only admins may create `type ∈ {admin, global}`
(`:180-187`); **the `PUT` handler has no equivalent check.**

**Exploitability.** A `manager` sends
`{"id":"<their webhook>","team_id":"<another team's id>","type":"global"}` and the update
succeeds — subject only to RLS, whose `discord_webhooks` policies for a manager are
`FOR ALL USING (EXISTS(… role IN ('admin','manager')))` with **no team condition**
(`database/complete-discord-portal-setup.sql:102-110`). The webhook is therefore moved to
another team or promoted to org-wide, redirecting that channel's future automated
notifications.

**Impact.** A team-scoped manager gains influence over another team's or the whole
organisation's Discord communications channel.

**Affected scope.** Discord notification routing; organisational communication integrity.

**Severity.** HIGH · **Confidence.** HIGH

**Recommended remediation.** Explicit field allowlist on every update
(`hook_url` is the only mutable field besides `active` and `channel_name`); scope (`team_id`,
`type`) is **server-assigned and immutable**; re-assert the type-elevation check on every write;
add `WITH CHECK` policies that bind `team_id` to the caller's own team.

## F-API-09 — HIGH — The entire Discord bot surface is guarded by one replayable static key with a fail-open edge case

**Finding.** Thirteen handlers in twelve files each declare their own copy of
`validateBotApiKey`, comparing the `Authorization` header to `` `Bearer ${process.env.RAPTOR_BOT_API_KEY}` ``.

**Evidence.** `app/api/discord/tryout/apply/route.ts:5-13` (and 11 sibling files):
```ts
function validateBotApiKey(request: NextRequest) {
  const apiKey = request.headers.get('authorization')
  const expectedKey = `Bearer ${process.env.RAPTOR_BOT_API_KEY}`
  if (!apiKey || apiKey !== expectedKey) { return false }
  return true
}
```

**Defects.**
1. **Fail-open when the variable is unset.** If `RAPTOR_BOT_API_KEY` is undefined,
   `expectedKey` is the literal string `"Bearer undefined"` — so any request sending
   `Authorization: Bearer undefined` is **authenticated**. The library version of this function
   *does* guard against it (`lib/discord-bot-auth.ts:13-17`), but **none of the 12 local copies
   replicate the guard**, and the library is never imported.
2. **Replayable.** No timestamp, nonce or signature; a captured header is valid indefinitely.
3. **Single point of compromise** across tryout announcement, invitation, evaluation,
   performance upload, attendance marking, and team performance/attendance reads.
4. **Non-constant-time comparison** (`!==`), permitting a timing side channel on the secret.
5. **No identity attribution** — bot writes land with `triggered_by = NULL`, so there is no
   non-repudiation and no way to tell which integration performed an action.
6. **No rate limiting** anywhere, so a leaked key yields unlimited write access to
   `performances`, `attendances` and the tryout pipeline.
7. **Duplicate implementations** — 12 copies of a security control is 12 opportunities to
   introduce a defect, and one already has.

**Exploitability.** Conditional on the env var being unset (deterministic) or the key leaking.

**Impact.** Unauthorised creation of tryouts, invitations and evaluations; falsification of
recruitment records; injection of fabricated performance and attendance data.

**Affected scope.** The entire Discord bot integration and the tryout pipeline.

**Severity.** HIGH · **Confidence.** HIGH

**Recommended remediation.** Replace with per-integration credentials and signed requests
(timestamp + nonce + HMAC over method, path, body hash and timestamp), reject stale timestamps
and replayed nonces, verify the key's presence before comparing, use
`crypto.timingSafeEqual`, centralise verification in one module, add rate limits, and attribute
every call to a service identity recorded in the audit log.

## F-API-10 — MEDIUM — PostgREST filter injection in profile search

**Finding.** A caller-supplied query string is interpolated directly into a PostgREST `.or()`
filter expression.

**Evidence.**
```ts
// app/api/profile/search/route.ts
:52   queryBuilder = queryBuilder.or(`
:53     full_name.ilike.%${query}%,
:54     display_name.ilike.%${query}%,
:55     email.ilike.%${query}%,
:56     bgmi_id.ilike.%${query}%
:57   `)
```
`query` is `url.searchParams.get('q')` (`:20`) with no escaping. A value containing `,` or
`)`, or PostgREST operator syntax, is parsed as additional filter predicates rather than as
literal text.

**Exploitability.** Requires an `admin` or `manager` token (`:15`). Not exploitable by an
anonymous caller.

**Impact.** Filter manipulation — the caller can broaden or reshape the predicate set. Impact is
bounded by the fact that the endpoint already grants broad read access to those roles, and by
RLS. The real cost is that the pattern is a **template** for injection into every future
`or()`/`filter()` call.

**Affected scope.** The search endpoint; the coding pattern.

**Severity.** MEDIUM · **Confidence.** MEDIUM

**Recommended remediation.** Escape user input for PostgREST (`%` → `\%`, `,` → `\,`,
`.` → `\.`, `(`/`)`), or better, move search to a server-side function or a Postgres
`tsvector`/trigram index with a bound parameter. Also cap `limit` (`:24` has no upper bound) and
switch the query to the user-scoped client rather than the anon client (`:27`), which currently
makes the endpoint non-functional anyway.

## F-API-11 — MEDIUM — Unauthenticated public endpoints relay content to a credential and have no rate limit

**Finding.** `POST /api/public/submit/contact` and `POST /api/public/submit/application` accept
arbitrary JSON from anonymous callers and relay it, server-side, to the organisation's Discord
channel using a webhook credential held in a `NEXT_PUBLIC_*` variable.

**Evidence.** `app/api/public/submit/contact/route.ts:45`
`let webhookUrl = process.env.NEXT_PUBLIC_CONTACT_WEBHOOK_URL || process.env.NEXT_PUBLIC_PUBLIC_WEBHOOK_URL`;
`:46-64` service-role fallback that resolves `admin_config.default_public_webhook_id` →
`discord_webhooks.hook_url`; `:71-75` `fetch(webhookUrl, { method: 'POST', … })`; `:79` returns
the upstream Discord error text to the caller.
`app/api/public/submit/application/route.ts:33-43` — identical shape.

**Exploitability.** Trivial.

**Impact.**
* **Channel flooding / spam** at a rate limited only by Discord's own limits.
* **Phishing and social engineering** using the organisation's webhook identity and branding.
* **Webhook-URL disclosure** via the `NEXT_PUBLIC_*` bundling (see `19_SECRETS.md` F-SEC-01).
* **Error-based information disclosure** of Discord responses.
* No record of the submitter beyond what the caller chooses to send; no consent capture.

**Affected scope.** The public intake channel and the exposed webhook credential.

**Severity.** HIGH · **Confidence.** HIGH

**Recommended remediation.** Persist submissions to a server-side `intake_submissions` table
first; deliver to Discord asynchronously via a queue; rate-limit per IP with progressive
backoff; add a proof-of-work or CAPTCHA challenge; never hold the delivery credential in a
`NEXT_PUBLIC_*` variable; rotate the existing webhook.

## F-API-12 — MEDIUM — Public endpoint returns fabricated metrics and can leak aggregate spend

**Finding.** `GET /api/public/stats` is unauthenticated and returns a mixture of real database
aggregates and **hardcoded fabricated figures**.

**Evidence.**
```ts
// app/api/public/stats/route.ts
:22-30  teams / users / performances / placement=1 / slot_expenses.total   (anon client)
:55     const baseUnderdogPractice = 37800
:56     const baseMatches = 3240
:57     const baseWWCD = 1134
:59     const costCovered = baseUnderdogPractice + expensesSum
:60     const totalMatches = baseMatches + liveMatches
:61     const totalWWCD = baseWWCD + liveWWCD
:63-70  returned to the public
```
Three further problems: (a) `liveWWCD` is `COUNT(performances WHERE placement = 1)`, which is a
**different metric** from WWCD (wins/wins/close denies) — a BGMI term; (b) `costCovered`
conflates a hardcoded number with real `slot_expenses.total`, i.e. **real financial data is
added to a fabricated figure and published**; (c) `select('total')` with no limit loads every
expense row.

**Exploitability.** Trivial.

**Impact.** The organisation's public website presents numbers that are not measurements. For
a commercial esports organisation this is a marketing-claims integrity problem and a potential
consumer-protection issue, and it will be wrong for any future tenant. Aggregate spend may also
be disclosed if RLS is not enforced.

**Affected scope.** Public credibility; potential financial disclosure.

**Severity.** MEDIUM (HIGH as a brand/integrity matter) · **Confidence.** HIGH

**Recommended remediation.** Delete the fabricated constants. If public statistics are wanted,
compute them from real data, publish them on a cache with an explicit "as of" timestamp, and
have them reviewed as marketing claims. Never publish spend.

## F-API-13 — MEDIUM — Raw database and framework error text is returned to clients

**Finding.** At least ten handlers place the raw Supabase/PostgREST error message into the
response `details` field, and the root error boundary renders `error.message` to the user.

**Evidence.** `app/api/performances/route.ts:46, 127, 295`;
`app/api/sessions/route.ts:90, 209`;

`app/api/public/submit/contact/route.ts:79`;

**Exploitability.** n/a — an information leak, not an exploit.

**Impact.** Leaks table and column names, constraint names, RLS policy behaviour and internal
structure. This materially assists the exploitation of every other finding in this document: an
attacker learns the schema from error messages.

**Severity.** MEDIUM · **Confidence.** HIGH

**Recommended remediation.** Return a stable, generic error code plus a correlation id; log the
detail server-side; render a production-safe message in the boundary.

## F-API-14 — MEDIUM — No rate limiting, pagination or idempotency anywhere

**Finding.** The application has **zero** rate limiting, **zero** enforced pagination and
**zero** idempotency protection on writes.

**Evidence.**
* `lib/discord-bot-auth.ts:51-75` defines `RATE_LIMITS` (performance 60/min, attendance 30/min,
  queries 100/min, tryouts 10/min) — and it is **never imported** (verified: the only matches
  are inside that file).
* `lib/api-utils.ts:227-237` `getPaginationParams` (caps limit at 100) — **never imported** by
  any route (verified).
* `app/api/profile/search/route.ts:24` `parseInt(… || '20')` with no cap.
* `app/api/performances/route.ts:63` limit ≤ 1000, and `limit=0` (the default) means
  **unbounded**.
* `GET /api/attendances`, `/api/sessions`, `/api/rosters`, `/api/slots` return unbounded sets.
* No `Idempotency-Key` handling anywhere.
* The five check-then-insert races in `15_DATABASE_QUALITY.md` §8 are direct consequences.

**Exploitability.** Trivial for the public endpoints; trivial amplification for the rest.

**Impact.** Cost exhaustion, database load, webhook flooding, duplicate records, and a poor
foundation for billing (usage metering requires accurate, deduplicated counts).

**Affected scope.** Every endpoint.

**Severity.** MEDIUM · **Confidence.** HIGH

**Recommended remediation.** Edge-level rate limiting keyed on identity **and** IP, with
per-endpoint budgets; mandatory cursor pagination with a hard server-side cap; `Idempotency-Key`
on every write with a server-side dedupe table; unique constraints backing each idempotent
operation.

## F-API-15 — MEDIUM — Webhook URLs are returned to the browser and opened in a tab

**Finding.** The Discord webhook credential is rendered into the DOM and launched in a new
browser tab by the management UI.

**Evidence.** `app/dashboard/discord-portal/webhooks/page.tsx:394` renders the value into an
`<Input>`; `:490`
`<Button … onClick={() => window.open(webhook.hook_url, '_blank')}>`.

**Exploitability.** n/a directly; it makes the credential trivially copyable by any manager and
guarantees it is present in the DOM, in any XSS payload harvest, and in browser history.

**Impact.** Institutionalises credential exposure; contradicts any encryption-at-rest plan;
a manager's session compromise becomes immediate channel compromise.

**Severity.** MEDIUM · **Confidence.** HIGH

**Recommended remediation.** Never return a webhook URL. Store it encrypted; return only a
masked hint and an opaque identifier; offer "replace" and "test" actions that operate
server-side. Delete the `window.open` affordance.

## F-API-16 — MEDIUM — CORS is declared as `*` on a subset of endpoints

**Finding.** `corsHeaders` sets `Access-Control-Allow-Origin: *` and is applied by 12 routes
via `handleCors`; the remaining 46 apply no CORS handling at all.

**Evidence.** `lib/api-utils.ts:240-244`; applied in `app/api/{users,performances,attendances,
sessions,slots,rosters,teams/*,tryouts,tier-defaults,profile,admin/settings}/route.ts`.
Additionally `middleware.ts:16-21` contains a second `Access-Control-Allow-Origin: *` block that
is **dead code**, because `middleware.ts:36`'s matcher
`'/((?!_next|api/|favicon.ico|assets|.*\\.(?:svg|png|jpg|jpeg|gif|webp|ico)).*)'` excludes
`api/` from the middleware entirely.

**Exploitability.** The browser will not attach credentials to a wildcard cross-origin request
unless the code opts in, and the token is in JS rather than a cookie, so the practical impact is
limited. The real exposure is that **any origin can read unauthenticated endpoints' responses**
(the `public/*` routes) and can read the responses of the 12 CORS-enabled routes if the caller
attaches the Bearer token itself — which a malicious page cannot do without the token.

**Impact.** Inconsistent, unnecessary cross-origin access; a latent risk if the session ever
moves to a cookie (which it must, per `09_AUTHENTICATION.md` F-AUTH-01), at which point
`ACAO: *` would become an immediate credential-theft vulnerability.

**Affected scope.** 12 endpoints today; all endpoints after the session moves to cookies.

**Severity.** MEDIUM · **Confidence.** HIGH

**Recommended remediation.** Remove `corsHeaders` entirely unless a specific cross-origin
consumer exists; if one does, use an explicit origin allowlist plus `Vary: Origin` and
`Access-Control-Allow-Credentials: true`; delete the dead block from `middleware.ts`.

## F-API-17 — LOW — The session endpoint echoes the caller's own token

**Finding.** `GET /api/auth/session` returns `{ access_token: <the token the caller just sent> }`
when no server-side session is found.

**Evidence.** `app/api/auth/session/route.ts:45-47`
`return createSuccessResponse({ session: session || { access_token: token } })`.
It also uses `supabase.auth.getSession()` on a client that has no persisted session
(`:33`), so the "session" branch is effectively unreachable.

**Exploitability.** n/a — the caller already possesses the token.

**Impact.** An endpoint that appears to validate sessions but does not, and that returns
credential material in a response body (increasing the chance of it appearing in logs,
proxies and browser history). Its only real caller is `app/debug/page.tsx` and
`app/debug-simple/page.tsx`, which are being deleted.

**Severity.** LOW · **Confidence.** HIGH
**Recommended remediation.** Delete the endpoint and both debug pages.
