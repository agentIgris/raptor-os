8. RELATIONSHIP CLASSIFICATION
------------------------------
ONE-TO-ONE
  (none enforced; users and profiles would be 1:1 in intent only)

ONE-TO-MANY
  teams -> rosters / sessions / slots / winnings / tryouts
  users  -> performances / attendances / user_agreements
  tryouts -> tryout_applications -> tryout_evaluations / tryout_invitations
  slots   -> slot_expenses / winnings / performances

MANY-TO-MANY
  users <-> teams, via rosters          (no join table metadata)
  users <-> tryouts, via tryout_applications
  teams <-> tryouts, via the team_ids ARRAY (no FK, no metadata)  (!)

REDUNDANT
  users.team_id  <->  rosters.team_id            two sources of truth
  performances.slot (uuid, no FK)  <->  performances.slot_id
  profiles  <->  users             the same human, twice
  users.password  <->  auth.users.encrypted_password

ORPHANABLE
  attendances.session_id (nullable, no ON DELETE behaviour declared)
  performances.team_id (nullable), performances.slot / slot_id
  rosters.team_id / rosters.user_id
  tryout_applications.user_id  (applicant has no users row)
  tryouts.team_ids uuid[]       (array cannot be constrained)
  winnings.slot_id (nullable)
  holidays                        (referenced by nothing)

CIRCULAR
  users.team_id  ->  teams.id
  teams.coach_id -> users.id
  Both nullable and unenforced: a user can belong to a team that they
  themselves coach, with no constraint and no way to detect it.

MISSING CONSTRAINTS (summary)

  UNIQUE(session_id, user_id) on attendances
  UNIQUE(user_id, slot_id) on performances
  UNIQUE(user_id, agreement_type) on user_agreements

  FK on performances.slot
